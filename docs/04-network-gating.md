# 04 · 酒店网络门控

## 为什么需要

把路由器带到酒店后，典型流程是：连酒店 WiFi（中继）→ 打开浏览器 → 被重定向到认证页 →
输入房号/手机号 → 才能上网。这里有两个陷阱：

1. **拨到 ON 时还没有网。** 核心照样启动，加载完规则后发现没有任何出口，
   代理端口在监听但什么都连不上；这期间内存被打满，很容易触发 OOM。
2. **认证页会被代理破坏。** 如果代理已经在跑，手机/电脑的流量被规则拦截转发，
   酒店的 302 重定向到认证页这一步直接失败 —— 于是"网明明连着，就是打不开认证页"。
   拔掉代理反而能认证。

所以门控策略是：**没网就不起核心；要认证就先停核心；通了再起。**

## 三态探测

```sh
PROBE_URLS="http://connect.rom.miui.com/generate_204
            http://www.gstatic.com/generate_204
            http://cp.cloudflare.com/generate_204"
```

每个地址期望 **HTTP 204 且无响应体**。判定：

| 结果 | 含义 | 动作 |
|---|---|---|
| 任一返回 204 | 在线 | 启动/保持核心 |
| 有 HTTP 应答但码不是 204（200/302/…） | 被劫持，多半是 captive portal | 停核心，等认证 |
| 三个都无应答（`000`） | 离线（没连上 WiFi / 中继没起来） | 停核心，等恢复 |

设计取舍：

- **必须用 HTTP 而不是 HTTPS。** 强制门户靠拦截明文 HTTP 302 实现；用 HTTPS 时
  被 MITM 会得到 TLS 错误（curl 返回 `000`），那就分不清"离线"和"要认证"了。
- **`generate_204` 而不是 `baidu.com`。** 只需要状态码，不需要下载内容，
  5 秒超时也不会拖慢开关动作。
- **三个点分散在不同 AS。** 单个域名被酒店 DNS 劫持/屏蔽时仍能判定。
- **只要有一个 204 就认为在线**，宁可漏判也不误判（误判成 portal 会停掉正常工作的核心）。

> 两个脚本的严格程度不同，这是有意的：
> 开关模块（`openclash.sh`）把**任何非 204 的 HTTP 应答都当 portal**，因为它要决定
> "要不要让代理接管全部流量"，宁严勿松；自动更新脚本（`openclash-auto-update.sh`）
> 只在 `200 + body 含 <html` 时才判 portal，因为它只需要判断"能不能下载"，
> 宽松一点可以避免无谓跳过。

## 决策表

| 探测结果 | 核心状态 | 动作 |
|---|---|---|
| 在线 | 未运行 | `start_clash`（21s 左右稳定） |
| 在线 | 运行中 | 不重启，只补指示灯；watcher 记心跳 |
| 认证页 | 运行中 | **先 `stop_clash`**，日志提示去浏览器认证 |
| 认证页 | 未运行 | 只记日志，不起核心 |
| 离线 | 运行中 | `stop_clash`，等网络恢复 |
| 离线 | 未运行 | 只记日志 |

不论哪一行，`do_on` 结束前都会 `watch_start`，所以"等"这件事是有守护的，
不需要人再拨一次。

## 掉网分级

运行中掉网有两种，处理力度不同：

| 判据 | 含义 | 处理 |
|---|---|---|
| `ip route` 没有默认路由，或网关 ping 不通 | 上游真的断了（离开酒店、中继掉线） | **立即**停核心 |
| 链路正常但外网不通 | 可能是认证过期、节点失效、DNS 故障 | 连续 **3 次**（约 1 分钟）才停核心 |

为什么要分：认证页刚消失、节点短暂抖动都会让外网短暂不通，一掉网就停核心会导致
代理反复启停（每次 20s+，还伴随内存峰值）。给 3 次机会能滤掉大部分抖动。

## watcher 状态机

每 `WATCH_INTERVAL`（默认 20s）跑一轮：

```
        ┌──────────── 在线 ────────────┐
        │  核心不在 → start_clash       │
        │  核心在   → 记 online         │
        ▼                               │
   认证页 portal ──► 停核心 ──► 等认证 ──┘
        ▲                               │
        └──── 离线 offline ◄────────────┘
              停核心，等链路
```

- 状态变化才写日志（`_last` 比对），避免每 20s 刷一行同样的内容
- 每 15 轮写一条心跳：`watcher 心跳：状态=offline 连续失败=0 clash_pid= 可用内存=142MB`
- `uci openclash.config.enable != 1`（用户拨回 OFF）→ 自己退出

## 酒店里的实际用法

1. 插电，路由器起来。此时拨杆在 OFF → 核心不跑，灯灭（省电省内存）。
2. GL 后台把 WiFi 设成中继（Repeater）连酒店 AP。能连上但上不了网是正常的。
3. 手机/电脑连路由器的 WiFi。
4. **先拨到 ON。** 日志会写 `需要网页认证` 或 `外网不通`，核心不启动。
5. 浏览器打开任意 `http://` 地址 → 跳到酒店认证页 → 完成认证。
6. watcher 在 20 秒内探测到 204 → 自动启动核心，代理就绪。
7. 退房前拨到 OFF：核心停、灯灭、watcher 退出。

如果酒店**不用认证**（比如房间网线、或已开放），第 4 步拨 ON 就直接启动核心，不需要第 5 步。

如果是**每次联网都要重新认证**的酒店：认证过期后 watcher 会检测到 portal 并停掉核心，
你重新认证后自动恢复，不用管拨杆。

## 调试

```sh
# 看当前判定
sh /etc/gl-switch.d/openclash.sh status | grep -E '外网探测|上游|后台守护'

# 模拟离线
OCSW_PROBE_URLS='http://127.0.0.1:9/generate_204' sh /etc/gl-switch.d/openclash.sh on

# 模拟认证页（本机 nginx 根路径返回 HTML 200）
OCSW_PROBE_URLS='http://127.0.0.1/' sh /etc/gl-switch.d/openclash.sh on

# 缩短轮询便于观察
OCSW_WATCH_INTERVAL=6 sh /etc/gl-switch.d/openclash.sh watch
```

注意 `upstream_info` 里的 `repeater=connected portal=false` 来自
`ubus call repeater status`，它反映的是**中继模块**的状态（含 GL 自己对 portal 的判断），
和我们用 curl 探到的是两套信息，可以互相印证。
